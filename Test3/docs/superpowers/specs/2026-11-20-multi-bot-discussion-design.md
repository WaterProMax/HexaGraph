# 多 Bot 群聊讨论：从想法到需求规格审批

日期：2026-11-20　状态：设计已通过，待写实现计划

## 背景与范围

用户给出一句简短的想法，项目里的多个 Bot 先各自独立出方案，再互相打分，分数接近后交给 Leader 审核，Leader 通过后弹框请用户审批完整需求规格。用户不满意就打回重新讨论，满意则进入任务拆解。

整个功能拆成两个子项目，各自走设计、计划、实现：

1. **本文：讨论到需求规格审批的闭环**（群聊讨论、互评打分、Leader 审核、用户审批、打回）。
2. 任务拆解与可视化编排器（另起设计文档，批准后才进入；本文只留一个占位状态）。

参考材料：`第一组--多体讨论工作流设计.docx`（第 4 章讨论、第 7 章评价、第 8 章需求规格）、`Test3/docs/API.md` 的 P4 讨论章节。

## 已确认的决策

1. 讨论**全自动运行**：Bot 自己出方案、互评、必要时多轮修改，群聊实时滚动。用户只在审批弹框介入，中途只能暂停或终止，不能插话。
2. 收敛规则**两个条件同时满足**才交 Leader：各方案总分差在阈值内，且三个硬门槛全部通过。不满足就再来一轮互相修改，最多 3 轮；到顶强制交 Leader 并标注未达成一致。
3. 完整需求规格由 **Leader 综合**各方案、评分和分歧写成，未解决的分歧单独列出供用户裁决。
4. 采用**阶段式项目页**：项目工作台顶部一条流程条，主区域按阶段切换。

## 流程与状态

流程条：`想法 → 独立方案 → 互评 → Leader 审核 → 你的审批 → 任务拆解`。

与后端讨论状态的对应：

| 流程条步骤 | 后端状态 |
|---|---|
| 想法 | 无会话 / `draft` |
| 独立方案 | `grouping`、`round1_independent` |
| 互评 | `cross_review`、`round_n_revise` |
| Leader 审核 | `converged_pending_human` 且决策包尚未提交 |
| 你的审批 | `converged_pending_human` 且决策包已提交 |
| 任务拆解 | `approved`（本期只显示“规格已批准，等待任务拆解”） |

`rejected` 与 `budget_exhausted` 不是流程条上的步骤：打回后新建会话并回到“独立方案”；预算耗尽按“强制交 Leader”处理。

## 页面

### 项目刚建好

主区域只有“一句话想法”输入框和“开始讨论”。项目里没有 Leader，或成员少于 2 个 Bot 时按钮不可点，提示“先邀请 Bot”，指向现有的“邀请 Bot”按钮。

### 讨论进行中

左右两栏：

- **群聊时间线（左）**：带头像的气泡，四种类型：系统提示、方案提交、评分卡、Leader 发言。
- **进度与评分（右）**：当前轮次 `n / 3`；评分表（行为被评方案，列为评委，显示总分和“分差 / 阈值”）；三个硬门槛的勾选状态；“暂停”“终止”（终止需二次确认）。

盲首轮期间时间线只显示“已提交方案（内容已封存）”，不显示正文；交齐解封后气泡可展开看全文。这与后端封存规则一致，避免先发言者带偏他人。

### Leader 审核

在群聊里可见。收敛后 Leader 读各方案、评分和分歧，写出完整规格并自查：

- 满意：提交给用户。
- 不满意：在时间线写一条“还需要再改一轮”，回到互评。这一轮计入 3 轮上限。
- 3 轮到顶仍不满意：强制提交，并在规格里标明未解决的问题。

### 审批弹框（“需求规格待你审批”）

Leader 提交决策包后自动弹出，宽约 880px，内容区单独滚动：

- 顶部摘要标签：第几轮、分差、硬门槛 3/3、未解决分歧条数。
- 正文用 Markdown 渲染完整规格。结构按 docx 第 8 章：功能列表、验收标准、非功能需求、本版不做、还没定的问题，每条功能注明来源编号。
- 折叠区：“未解决分歧”（列出各 Bot 的立场）、“评分汇总”。
- 底部：左“打回重新讨论”，右蓝色“通过，进入任务拆解”。
- 关闭弹框（✕ 或 Esc）只表示稍后处理，不做决定；页面顶部保留“待你审批”横幅，可随时再打开。

### 打回

- 点“打回”后展开必填的意见输入框，填写后才能提交。
- 意见与想法、上一版规格一起作为下一次讨论的输入。
- 时间线不清空，用分隔线隔开：`第 2 次讨论 · 你的意见：……`，流程条回到“独立方案”。
- 打回次数不设上限，页面显示“第 N 次审批”。

### 通过

- 规格写入项目基线，流程条走到“任务拆解”。
- 项目页新增“需求规格”入口，只读查看已批准的规格和历史版本（含被打回的版本）。
- 任务拆解本身不在本期范围。

## 后端新增

本期与前端一起做，否则前端没有数据可显示。

1. **讨论驱动器**：创建会话后在后台自动运行。
   - 每个 Bot 用自己的模型与 API Key 独立写方案（沿用 `call_agent` 与冻结的 Bot pin）。
   - 方案交齐后，每个 Bot 给别人的方案打分，输出分数、理由、三个硬门槛和异议。
   - 判断收敛；不通过则开 revise 轮；通过后 Leader 综合写规格并自查，再提交决策包。
   - 支持暂停、继续、终止（终止需 `confirm: true`）。
2. **消息流**：新表 `discussion_messages`（会话 ID、序号、类型 `system|proposal|review|leader`、Bot、轮次、负载、时间）；`GET /api/discussion-sessions/{sid}/messages?after=`；SSE `GET /api/discussion-sessions/{sid}/events`，沿用 `Last-Event-ID` 续传约定。
3. **收敛规则**：`should_converge` 增加“按方案汇总的总分差 ≤ 阈值，且硬门槛全过”。阈值放进 `DiscussionBudget.score_gap_threshold`，默认取满分的 10%。`score_spread` 改为按方案汇总。此项**推翻** `API.md` 中“分数不参与收敛”的契约，需同步更新 `API.md`、测试和 OpenAPI 快照。
4. **持久化**：会话增加想法原文、上一次会话 ID、用户打回意见；新增 Alembic 迁移 `0012`（含消息表）。
5. **控制路由**：`POST /api/discussion-sessions/{sid}/pause|resume|terminate`。

沿用现有约定：路由请求头 `X-Bot-Id`，审批 `resolve` 仍以 Leader 身份调用（项目页的操作身份固定为 Leader）；错误体 `{"error_category","detail"}`。

## 错误处理

- **Bot 调用失败**：时间线出现系统气泡写明原因，自动重试 1 次；仍失败则暂停，右栏出现“重试”和“跳过此 Bot”。跳过后参与者少于 2 人则终止。
- **评分输出不是合法格式**：重试 1 次，仍失败则该评委弃权并提示。
- **预算耗尽或 3 轮到顶**：强制交 Leader，标注“未达成一致”。
- **SSE 断线**：自动重连并按序号续传。

## 测试

- **后端**：用已有 `scripted` 模型提供者覆盖：一轮收敛、两轮收敛、3 轮强制提交、打回重来、Bot 调用失败；收敛规则的单元测试；迁移 `0012` 升降级；OpenAPI 快照。
- **前端（vitest）**：阶段推算；盲首轮不显示正文；分差计算；审批通过与打回（意见必填）；关闭弹框不做决定；SSE 断线续传；少于 2 个 Bot 时的提示。
- **端到端**：1 条 Playwright（scripted 提供者）。

## 已知限制

- 任务拆解与编排器不在本期，批准后只显示占位状态。
- 打回次数不设上限；若后续发现讨论反复空转，再加软提示。
- 每份方案上限 6000 字符，用来保证评委的上下文放得下所有方案：超出时驱动器要求该 Bot 重写一次，仍超出则截断并在气泡上标注“已截断”。该上限先写死，不做成可配置项。
