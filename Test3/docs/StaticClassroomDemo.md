# 静态课堂演示：自习室座位查询

> **状态：已下线（只读历史）。** 独立页面、侧栏入口、路由渲染与预置素材已移除；`/workstation/static-classroom` 只显示下线说明，不会挂载演示或触发任何运行。本文保留为历史设计与讲解记录，不再作为当前操作指南；当前工作台用法见 `Test3/README.md`。

> 本案例是人工编写的完整静态教学案例，不代表真实模型端到端能力，也不是真实代码执行或业务系统验收证明。

## 1. 启动

只需启动 Test3 前端；本路由不依赖后端、模型密钥或付费 API。依赖已安装时，在仓库根目录执行：

```bash
npm --prefix Test3/frontend run dev -- --host 127.0.0.1 --port 5173
```

访问：

```text
http://127.0.0.1:5173/workstation/static-classroom
```

也可以打开原工作台后，在左侧导航选择“静态课堂演示”。真实工作台和后端启动方式保持不变，见 `Test3/README.md`。

### 数据隔离与刷新行为

- 案例数据全部在前端固定夹具中，不创建后端项目，不进入真实运行列表。
- 播放进度只写入本案例专用的浏览器 localStorage，不读取或修改真实运行数据。
- 刷新页面恢复同一演示运行、讨论条数、关卡、任务状态和活动记录；刷新后自动播放保持暂停，需手动继续。
- “重新演示”只新建本案例的下一次静态运行，清空本案例旧讨论、任务和活动，不删除任何真实数据，也不消耗 scripted 队列。

## 2. 课堂操作

1. 点击“开始静态演示”。固定需求可折叠查看，页面持续显示“静态课堂演示 · 预置数据 · 不调用真实模型”。
2. 点击“下一步”逐条展示讨论，或点击“自动播放”。打开“讨论”页签，查看产品、架构、开发、测试四类角色的 10 条人工编写发言。
3. 重点讲解两处争议：
   - D-01：产品提议预约，架构和开发指出身份、时段与并发冲突会扩大范围，最终只查询、不预约。
   - D-02：开发最初只突出实时数量，测试指出数据陈旧风险，最终补充更新时间和失败重试。
4. 讨论结束后自动停在“讨论结论确认”。查看已采纳、暂缓事项、验收要点，再点击“批准并推进”。
5. 依次查看并批准 SPEC、DESIGN、PLAN。自动播放不会代替人工批准；“驳回重写”在本静态案例中明确禁用。
6. PLAN 批准后，流程图显示五项任务及相同 ID、标题、角色、依赖和状态：

   ```text
                       ┌── T-02 预置查询服务 ──┐
   T-01 查询契约 ──────┤                      ├── T-04 前后端联调 ── T-05 场景验收
                       └── T-03 座位列表页面 ──┘
   ```

7. 为清楚展示并行，建议 PLAN 后改用手动“下一步”：

   | PLAN 批准后点击次数 | 画面状态 |
   | --- | --- |
   | 0 | T-01 ready，其余 pending |
   | 1 | T-01 running |
   | 2 | T-01 done；T-02、T-03 ready |
   | 3 | **T-02、T-03 同时 running；T-04 pending** |
   | 4 | T-02 done；T-03 running；T-04 仍 pending |
   | 5 | T-02、T-03 done；T-04 ready |
   | 6–8 | T-04 running/done，随后 T-05 ready/running |
   | 9 | T-05 done，自动打开静态验收总结 |

8. “节点详情”展示预置摘要、示例产物和模拟结果；“活动”只记录静态演示事件，不是模型调用日志。
9. “暂停播放”只停止演示时间线。“暂停运行”是真实调度概念，本案例不支持，按钮保持禁用并附说明。
10. 点击“重新演示”可无限复位，无需重启前端或后端。

## 3. 约五分钟讲解脚本

### 0:00–0:35｜先声明证据边界

**操作：** 打开静态演示入口，展开固定需求。

**讲解：**
“今天演示的是 HexaGraph 的完整静态课堂案例。需求是自习室座位查询：按校区和楼栋查询，展示可用座位和更新时间，失败可以重试。请大家注意页面上的持续标识：所有讨论、任务和结果都是人工编写的预置内容，不调用真实模型，也不执行真实开发任务。本轮明确排除预约、支付和硬件接入。”

### 0:35–1:40｜多智能体如何形成方案

**操作：** 打开“讨论”，用“下一步”或“自动播放”展示前 3 条，再跳到 D-01。

**讲解：**
“产品先定义最短用户路径，架构统一座位快照契约，开发把实现拆成查询契约、服务和页面。这里的价值不是让多个角色重复说‘同意’，而是让角色从不同约束出发。D-01 中，产品提出预约，架构指出身份、时段和并发冲突，开发确认工作量会失控，所以最终把预约放到暂缓事项。”

### 1:40–2:20｜第二处分歧与讨论结论

**操作：** 展示 D-02 和讨论结论。

**讲解：**
“D-02 中，开发最初想只突出实时座位数，测试指出数据可能陈旧，要求显示更新时间和失败重试。最终结论会进入后续规格，而不是停留在聊天里。我们可以对照看到：已采纳事项对应 F1–F3，暂缓事项仍然排除，验收要点也与最后的三个场景一致。”

### 2:20–3:00｜人工确认与产物追溯

**操作：** 批准讨论，依次打开并批准 SPEC、DESIGN、PLAN。

**讲解：**
“时间线现在在人工关卡停下，自动播放不会替我批准。SPEC 固定需求边界，DESIGN 定义 M1–M4 和 C1 查询契约，PLAN 再分解成五项任务。这里复用工作台的关卡语义和规格产物视图，但所有内容仍明确标注为预置。”

### 3:00–4:10｜依赖、并行与汇合

**操作：** PLAN 后手动点击三次“下一步”，停在 T-02/T-03 同时 running；再点击两次展示 T-04 解锁。

**讲解：**
“T-01 是共同上游。完成后，T-02 查询服务和 T-03 列表页面先 ready，再同时 running，这就是依赖分叉后的并行。T-02 先完成时，T-04 仍然 pending；只有 T-03 也完成，T-04 才 ready。随后 T-04 联调、T-05 验收。节点详情中的摘要和结果同样是预置内容，未真实执行。”

### 4:10–5:00｜静态验收、活动与可重复播放

**操作：** 推进到验收，打开“活动”，最后点击“重新演示”。

**讲解：**
“最后的验收总结把需求、讨论决策、任务依赖、并行片段和三个预置场景放在一起，同时明确它们不计入仓库真实测试统计。活动页记录的是与画面一致的静态演示事件，不是模型调用日志。刷新会恢复当前进度；重新演示只复位本案例，因此课堂上可以反复播放。真实模型能力和真实业务执行仍需另行验收。”
