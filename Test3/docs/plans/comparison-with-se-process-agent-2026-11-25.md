## 一句话结论

对方赢在“**演示闭环**”：默认一条命令启动，需求进去、交付出来，中间有赛马、评审、甘特图、经验卡和可选的 Git 真实执行，老师很容易看懂“做完了”。

我们赢在“**工程深度**”：方案盲评、哈希基线、授权边界、证据分级、崩溃和解、测试量都明显更强。但我们的最后一段执行被安全边界挡住，README 又承诺了能跑，于是从外面看像“半成品”。

**下一步的重点不是继续加后端能力，而是把已有能力接通、演示出来、讲清楚。**

## 对方确实做得更好的地方

1. **默认路径能走完，而且明确说“这是模拟”。** `StewardPipeline` 一条消息串起分组、赛马、评审、融合、决策、规格、计划、开发、交付；默认 `gates=[]`，`Worker` 在未绑定仓库时返回 mock，交付时直接说明“本轮为模拟执行，没有生成真实源代码”。用户不会卡住。
2. **真实执行是一个可选档位，而不是“未完成”。** 绑定目标 Git 仓库后，模型按任务生成文件，`WorktreeAdapter` 建独立 worktree，`CommitVerifier` 校验可读性、祖先、上游 SHA 和路径范围，最后生成任务分支上的 commit；Docker 测试是可选增强，不是前置条件。
3. **计划可视化与可编辑性。** 甘特图、关键路径、分钟估时、依赖连线、并发上限、任务编辑、保存即新版本、运行绑定计划版本，这些都非常适合课堂演示。
4. **对话式主理人。** 暂停、继续、重试、改需求、重规划都能在聊天里说；旧方案和旧版本保留。演示时不需要满屏找按钮。
5. **经验/领域记忆产品化。** 经验卡有证据、有版本、有可见性、有发布/撤销和审计，能在下一个项目复用。
6. **启动与仓库状态。** 一条命令启动，`main` 干净，CI 至少覆盖后端，README 简洁清楚。老师打开 GitHub 就能看到同一份东西。

## 我们明显更强的地方

1. **需求讨论质量。** 五个角色、盲评、禁止自评、交叉评分、Leader 汇总、DecisionPackage 哈希，层层可追溯；对方默认模拟时很多主张是硬编码模板。
2. **文档链完整。** SPEC → DESIGN → PLAN 三段都有独立评审与审批门；对方没有独立 DESIGN 阶段。
3. **执行授权与安全。** legacy/granted_v1、统一入口授权、基线的哈希漂移失效、人工再批准、候选门 CAS、证据分级、`overridden` 不再冒充通过、崩溃和解与 attempt 绑定，这些是对方没有的。
4. **恢复与审计。** 重启和解、未决议 attempt 阻断、事件溯源、SSE 续传、发布/取代历史；对方主要是单进程 SQLite + 线程。
5. **测试深度。** 我们 889 项后端 + 427 项前端，覆盖授权、幂等、崩溃、候选、证据、讨论；对方 190 + 51，CI 还只跑后端。
6. **运行监控。** Twin Graph、任务级控制、缺陷、评分、评估 CSV、预算、trace；对方更像项目展示台，运维能力弱于我们。

## 对方也有明显硬伤，不要照抄

- 默认是 mock；真实执行要绑定仓库、配置模型，且交付只指向任务分支，不做最终合并/推送。
- Docker 测试可选，未配置时测试标“待实跑”；生成的应用从未真正启动过，验收仍带模型判断成分。
- React 工作台默认走 mock；`v2` 的 `/api/v2/projects/{id}` 没有实现，访问会 404 回退 mock，README 也承认运行/产物契约未对齐。真正完整的是单文件 HTML 工作台。
- 无鉴权，固定本地 actor；`/workspace/.../actions` 和 `/api/v2` 没有 token/CORS 防护。
- SQLite 单连接 + 单进程、线程派发，不适合多进程共享。
- 估时是模板常量；赛马模拟主张是关键词规则；主理人会自动替用户做产品决策。
- CI 只跑后端，前端测试和构建没有进入流水线。

3. **补齐“执行关闭”的 UI 状态。**

### P1：补齐对方最有演示价值的两块

5. **甘特图 + 关键路径 + 多方案对比视图。**
   - 后端只读暴露计划排期和 `critical_path`（已有纯函数），前端用点数映射估时或补 `estimate_minutes`；甘特图先只读，不做编辑。
   - 讨论页增加方案并排对比（主张、评分、分歧、采用/融合），数据已有。
   - 验收：PLAN 页能看时间轴、依赖、关键路径；讨论页能一屏比较 2–5 个方案。预计 3–5 天。

6. **把记忆闭环补上。**
   - 验收通过/导出时生成“项目复盘/经验卡”，带测试与缺陷证据，发布到项目记忆；下一次计划注入并显示命中。
   - 验收：第二次运行能在计划阶段引用第一次经验，且记录 usage。预计 2–3 天。

7. **做一条“本地真实执行”演示，或完成 granted 安全链。**
   - 低成本方案：新增仅本地启动的 demo launcher，用 `ExecutionPolicy(local_execution_authorized=True)` + 一次性示例仓库，展示真实 worktree、命令、commit、测试证据；产品 HTTP 安全闸保持关闭。
   - 彻底方案：完成 granted_v1 隔离 + grant + merge/accept，这条路成本高，不建议在演示前硬上。
   - 验收：演示能给出真实 commit 和测试输出，界面标注 `real_execution`，而不是把真实执行写成“模拟执行”。预计 1–2 天（演示方案）。

8. **计划编辑与候选门 UI。**
   - 不要直接改已批准基线：编辑生成新候选，走 `expected_revision` 和 SPEC 变更确认，再重新批准。
   - 同时把 reconcile、grant 列表、模块验收、release 下载接进 UI。
   - 验收：编辑计划 → 新候选 → 批准 → 运行绑定新版本；全程有审计。预计 3–5 天。

### P2：体验与契约

9. 统一命令栏/主理人式控制（暂停、继续、重试、改需求、重规划），底层仍调用现有确定性接口，不引入新的自由文本执行路径。
10. 统一错误契约与 API 文档；补 Idempotency-Key；补 release 下载入口；整理移动端与空状态。

## 建议给老师演示的顺序

1. `make demo` 启动，明确说“本轮模拟执行，不写真实仓库”。
2. 输入想法，展示五个角色盲评、交叉互评、Leader 汇总与你的审批。
3. 展示 SPEC、DESIGN、PLAN 三段文档和哈希基线；说明为什么不是“点一下直接写完”。
4. 展示甘特图/关键路径/多方案对比（P1 完成后）。
5. 展示模拟任务执行、任务级控制、证据分级和验收导出。
6. 如果老师追问“能不能真的改代码”，再启动本地真实执行演示，展示 worktree、commit、测试输出，并说明它只在一次性示例仓库里运行。

## 结论

对方是“**演示完成度**”做得更好，我们是“**工程完成度**”更深。老师觉得他们完好，是因为他们把“从需求到交付”的故事讲完整了；我们现在最缺的不是后端能力，而是：

1. GitHub 上的最新代码；
2. 一条不会在调度处断掉的默认演示路径；
3. 把已有能力可视化的几个关键视图（甘特图、方案对比、经验闭环）；
4. 一条能证明“真的能执行”的受控演示路径。

先完成 P0 的四件事，再按 P1 选两项做深，就足以在“完整度”上追上对方，同时保留我们在安全和审计上的优势。
